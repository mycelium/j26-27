# Задание 1. Умножение матриц

## Постановка задачи

- реализовать функцию `public static double[][] multiply(double[][] firstMatrix, double[][] secondMatrix);`
- вывести время выполнения для матриц большой размерности;
- оптимизировать время выполнения (описать в README применённые подходы).

## Запуск

Java 11+ умеет запускать одиночный `.java`-файл без явной компиляции:

```bash
cd j26-27/tasks/term-1/1
java MatrixMult.java
```

Эквивалентный вариант через компиляцию:

```bash
cd j26-27/tasks/term-1/1
javac MatrixMult.java && java MatrixMult
```

Программа ничего не читает из stdin и не требует аргументов: матрицы заполняются случайными числами внутри `main`, результаты замеров печатаются в консоль.

## Реализация

Класс `MatrixMult` содержит два метода умножения:

- `multiply` — базовый вариант;
- `multiplyOptimized` — оптимизированный вариант.

Оба принимают две матрицы `double[][]` и перед умножением проверяют их совместимость: обе должны быть прямоугольными, а число столбцов первой должно совпадать с числом строк второй, иначе бросается `ArithmeticException` с указанием размерностей. Размерности получаются через хелперы `rows`/`cols`, поэтому пустая матрица не приводит к `ArrayIndexOutOfBoundsException` при обращении к `matrix[0]`.

### Базовый алгоритм — `multiply`

Классический тройной цикл в порядке `i`–`j`–`r`:

```java
for (int i = 0; i < resRows; ++i)
    for (int j = 0; j < resCols; ++j)
        for (int r = 0; r < m; ++r)
            resMatrix[i][j] += firstMatrix[i][r] * secondMatrix[r][j];
```

Для каждой пары `(i, j)` вычисляется скалярное произведение строки `i` первой матрицы на столбец `j` второй. Сложность — `O(n³)`: `n³` умножений и сложений.

Проблема не в арифметике, а в доступе к памяти. Внутренний цикл идёт по `r`, то есть по **столбцу** `secondMatrix`. В Java `double[][]` — это массив строк, поэтому элементы `secondMatrix[0][j]`, `secondMatrix[1][j]`, … отстоят друг от друга на длину строки (при `n = 750` — 6 КБ). Почти каждое обращение попадает в новую кэш-линию, и процессор не может ни префетчить, ни векторизовать такую выборку. Дополнительно `resMatrix[i][j]` читается и записывается в память на каждой итерации внутреннего цикла.

### Оптимизированный алгоритм — `multiplyOptimized`

Тот же самый алгоритм, но с переставленным порядком циклов: `i`–`r`–`j`.

```java
for (int i = 0; i < resRows; ++i) {
    double[] aRow = firstMatrix[i];
    double[] resRow = resMatrix[i];
    for (int r = 0; r < m; ++r) {
        double air = aRow[r];
        double[] bRow = secondMatrix[r];
        for (int j = 0; j < resCols; ++j)
            resRow[j] += air * bRow[j];
    }
}
```

Теперь внутренний цикл идёт по **строкам**: `bRow` и `resRow` обходятся последовательно, без шага, а `air` вынесен в локальную переменную и живёт в регистре. Ссылки на строки `a[i]`, `res[i]`, `b[r]` берутся один раз на внешнюю итерацию, что избавляет от повторных разыменований.

Почему это быстрее базового варианта:

- **Локальность**: все три массива во внутреннем цикле читаются/пишутся непрерывно, поэтому кэш-линия используется целиком и аппаратный префетчер работает эффективно.
- **Меньше трафика памяти**: строка результата `resRow` (6 КБ при `n = 750`) остаётся в L1 на всё время внутреннего цикла, а не выгружается на каждую операцию.
- **Векторизация**: цикл `resRow[j] += air * bRow[j]` — это AXPY-подобная операция без зависимостей по данным между итерациями, она хорошо ложится на SIMD (это же ядро используется в BLAS/LAPACK).

Асимптотика остаётся `O(n³)` — константа уменьшается за счёт лучшей работы с кэшем, что и даёт ускорение в 4–6 раз на матрицах от 250 до 750.

## Измерение времени

Логика замера реализована в `main` и вспомогательных методах `measureMultiplyMillis` и `warmup`:

- **`Random(67)`** — фиксированное зерно генератора. Все запуски программы получают одни и те же матрицы `A` и `B`, поэтому разные версии алгоритма сравниваются на одинаковых данных, а результаты воспроизводимы между запусками.
- **Разные размеры** — `250`, `500`, `750`. Три точки нужны, чтобы видеть рост времени, соответствующий кубической сложности `O(n³)`, и то, как меняется ускорение с размером.
- **`System.nanoTime()`** — монотонные часы с наносекундным разрешением (в отличие от `currentTimeMillis()` они не зависят от смены системного времени). Замеряется только вызов умножения: время до вызова, время после, разница переводится в миллисекунды делением на `1_000_000.0`.
- **`warmup`** — 20 прогонов каждого метода перед замером. JVM выполняет первые вызовы интерпретатором и компилирует «горячий» код (C1, затем C2) асинхронно, поэтому без прогрева в результат попадает время компиляции, а не работы: на замерах это давало скачки ускорения от 1.1x до 8x на одном и том же коде. После 20 прогонов оба метода полностью скомпилированы, и замер отражает реальную скорость.

Для каждого размера выполняется один замер после прогрева. Ускорение считается как

```
speedup = elapsedBasic / elapsedOptimized
```

то есть «во сколько раз оптимизированный вариант быстрее»; значение больше 1 означает, что оптимизация работает.

## Результаты

Замеры выполнены на ноутбуке со следующими характеристиками (они важны для интерпретации: ускорение определяется в первую очередь размерами кэшей):

| Параметр | Значение |
|---|---|
| CPU | Intel Core Ultra 9 185H, 22 логических потока (P- и E-ядра) |
| Кэш L1d | 544 KiB (14 экземпляров) |
| Кэш L2 | 18 MiB (9 экземпляров) |
| Кэш L3 | 24 MiB (общий) |
| ОЗУ | 30 GB |
| ОС | Manjaro Linux, ядро 7.1.13 |
| JDK | OpenJDK 26.0.2.1 |

| Размер матриц | Базовый, мс | Оптимизированный, мс | Ускорение |
|---|---|---|---|
| 250 × 250 | 10.362 | 2.514 | 4.12x |
| 500 × 500 | 111.616 | 19.662 | 5.68x |
| 750 × 750 | 437.965 | 74.003 | 5.92x |

Время базового варианта растёт быстрее оптимизированного: при увеличении размера с 250 до 500 оно выросло в 10.8 раза против 7.8 у оптимизированного, поэтому ускорение увеличивается с 4.12x до 5.68x. Причина в том, что базовый вариант обходит вторую матрицу по столбцу, и чем больше матрица, тем чаще эти обращения промахиваются мимо кэша, тогда как оптимизированный читает память построчно. К 750 рост замедляется (4.12x → 5.68x → 5.92x): выигрыш от локальности упирается в размер кэша, и при `n = 1000` три матрицы по 8 МБ уже не помещаются в 24 МБ L3, после чего оба варианта ограничены пропускной способностью памяти.
