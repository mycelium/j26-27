# 1. Java: Matrix multiplication. Постановка задачи.

* реализовать функцию `public static double[][] multiply(double[][] firstMatrix, double[][] secondMatrix);`
* Вывести время выполнения для матриц большой размерности
* Оптимизировать время выполнения (описать в README применённые подходы)

## Функции

* `multiply(firstMatrix, secondMatrix)` -- оптимизированное умножение матриц: обход циклов i-k-j и параллельная обработка строк результата.
* `multiplyNaive(firstMatrix, secondMatrix)` -- базовое умножение матриц с обходом циклов i-j-k. Результат этой функции считается эталонным.
* `randomMatrix(rows, cols)` -- создание матрицы заданного размера, заполненной случайными числами в диапазоне от 0 до 1.
* `main(args)` -- генерирует две квадратные матрицы, трижды запускает обе версии умножения, выводит время выполнения каждой и проверяет, что результаты совпадают.

## Запуск

```
java MatrixMult.java          # матрицы 1000x1000 (по умолчанию)
java MatrixMult.java 2000     # матрицы 2000x2000
```

## Размерность матриц в тестах

В тестах перемножаются две квадратные матрицы размера **1000 × 1000** (≈ 10⁹ операций умножения-сложения). Размер можно изменить аргументом командной строки. Каждая версия запускается 3 раза на одних и тех же матрицах.

## Описание оптимизации

Изначально умножение реализовано тремя вложенными циклами в порядке i-j-k (функция `multiplyNaive`). В `multiply` применены два приёма.

### 1. Порядок обхода циклов i-k-j вместо i-j-k

Когда программа обращается к элементу массива, процессор подгружает в кэш не один элемент, а целый блок соседних адресов. Если следующий нужный элемент лежит рядом, он уже в кэше, и обращение почти бесплатное. Если далеко, приходится снова идти в оперативную память, что намного медленнее. Двумерный массив в Java хранится построчно: каждая строка это отдельный массив `double[]`.

При обходе i-j-k внутренний цикл идёт по `k` и читает `secondMatrix[k][j]`, то есть движется по **столбцу** второй матрицы. Каждый следующий элемент лежит в другой строке-массиве, далеко от предыдущего, поэтому кэш используется плохо.

При обходе i-k-j внутренний цикл идёт по `j` и работает с `secondMatrix[k][j]` и `result[i][j]`, то есть движется по **строкам** обеих матриц. Элементы лежат в памяти подряд, и каждая загруженная в кэш строка используется полностью. Значение `firstMatrix[i][k]` в этом цикле постоянно, поэтому оно читается один раз и вынесено в переменную `a`.

Порядок суммирования для каждого элемента результата при этом не меняется (по `k` по возрастанию), поэтому результаты обеих версий совпадают без погрешности.

### 2. Параллельная обработка строк

Строки результирующей матрицы вычисляются независимо друг от друга: строка `i` результата зависит только от строки `i` первой матрицы и всей второй матрицы, а записывает только в `result[i]`. Поэтому строки распределяются по потокам через `IntStream.range(0, rows).parallel()`, синхронизация не нужна.

## Результаты

Вывод программы (MacBook Air, матрицы 1000 × 1000):

```
Прогон 1: naive = 2149 мс, optimized = 105 мс, совпадают: true
Прогон 2: naive = 2045 мс, optimized = 59 мс, совпадают: true
Прогон 3: naive = 2080 мс, optimized = 69 мс, совпадают: true
```

| Версия | Среднее время, мс | Лучшее время, мс |
|---|---|---|
| `multiplyNaive` (i-j-k) | ≈ 2091 | 2045 |
| `multiply` (i-k-j + параллельность) | ≈ 78 | 59 |

Ускорение: ≈ 27 раз по среднему времени, ≈ 35 раз по лучшему.

Первый прогон оптимизированной версии медленнее остальных, так как в нём ещё идёт прогрев JIT-компилятора и запуск потоков.
